# 長時間処理の進捗可視化 実装計画

作成日: 2026-08-05
状態: 未着手（次セッションのワーカー向け）
対象: `grim_dawn_sync` / Windows 2端末運用
前提計画: `docs/implementation/save-sync-startup-visibility-plan.md`（T-A〜T-E 実装済み）

## 0. 背景（実機で発生した事象）

2026-08-05、`launch --exit-disposition restore-startup` の実機確認中に、
**同じ事象が 2 回発生した**。

- セッション `a344279d`（17:12）: `RESTORE_SESSION_START` 到達後、中断。
- セッション `6298f60b`（18:16）: `RESTORE_SESSION_START` 到達後、中断。

いずれも監査ログに `failed` 行が無い。すなわちハンドルされたエラーではなく、
プロセスが外部から強制終了されている。

利用者の報告によれば、直接の引き金は Grim Dawn 側の不具合
（キャラクター選択画面に戻り、再入場しようとしてロード画面でハング）であり、
利用者はゲームを手動でタスクキルした。**同期ツール自体の不具合ではない。**

問題はその後である。「起動前の状態に戻す」を選択したあと、ツールは
**約 75〜90 秒間、画面に一切何も表示せずに**作業する。
ゲームが固まってタスクキルした直後の利用者が、無言のまま 1 分半動かない
コンソールを見て「これも固まった」と判断するのは妥当な反応であり、
2 回とも異なる地点で中断していることが、決定論的ハングではなく
外部からの終了であることを裏付けている。

| セッション | staging 展開 | 置換前アーカイブ | stage コピー |
|---|---|---|---|
| `a344279d` | 891 完了 | 未作成 | なし |
| `6298f60b` | 891 完了 | 891 完了 | 891 完了 |

### 0.1 実測値（2026-08-05、実セーブ 891 ファイル / 約 20MB）

| 項目 | 実測 |
|---|---|
| `stable_manifest`（`retries=3`, `window_seconds=3`）1 回 | 4.2 秒 |
| コピー + 検証（session-start スナップショット）1 回 | 17.0 秒（2 セッションで同値） |

`restore-startup` の内訳（概算）:

| 処理 | 概算 |
|---|---|
| session-start アーカイブを staging へ展開 | 約 17 秒 |
| `plan_restore`（source / live の検証 2 回） | 約 8 秒 |
| `archive_before_restore`（丸ごとコピー + 検証） | 約 21 秒 |
| `apply_restore` の stage コピー（丸ごとコピー + 検証） | 約 21 秒 |
| ディレクトリ入れ替え + 最終検証 | 約 8 秒 |
| **合計** | **約 75〜90 秒** |

セーブ全体を 3 回コピーし、その都度ハッシュ検証していることが所要時間の主因である。

### 0.2 沈黙するのは restore-startup だけではない

同種の無言区間が他にもある。着手前に実測して一覧化すること。

- `SESSION_START_SNAPSHOT` → `START_DPYES`: **実測 17.0 秒**。
  「起動」を押してからゲームが立ち上がるまでの無言区間。
- `ARCHIVE_AFTER_GAME`: ゲーム終了後のアーカイブ。1 コピー + 検証。
- `publish` 経路の `snapshot` → `push`: Vault へのコミットと push。
- カタログ構築（`fetch` + 全候補の `validate_commit_snapshot`）:
  選択画面が出るまでの待ち。**ここは既に `load_catalog_in_worker` で
  ワーカースレッド化されており、Tk ウィンドウが出るまでの間だけである。**

## 3. T-F1: 事前の所要時間告知（最優先・最小コスト）

**この 1 つだけで今回の事象は防げた。** 他のチケットより先に完了させること。

無言区間そのものを無くすより、**無言区間が来ることを事前に伝える**ほうが
はるかに安く、かつ確実である。

### 3.1 対象

1. 終了後の disposition 確認ダイアログ（`selector_ui.present_exit_disposition_confirmation`）
   - `Restore start-of-session save` と `Keep local only` のボタン説明に、
     「この後アーカイブ処理に 1〜2 分かかることがあります。
     ウィンドウやコンソールを閉じないでください。」という趣旨の文言を加える。
   - 特に `restore-startup` は 3 回のコピーを伴うため最長である旨を明記する。
2. 選択画面（`present_tk_from_builder`）の「After the game exits」ラジオ
   - `restore-startup` の説明に所要時間の目安を添える。
3. 非対話（コンソール）経路
   - 長時間処理に入る直前に 1 行、標準エラーへ告知を出す（T-F2 と同じ機構でよい）。

### 3.2 文言の原則

- 具体的な秒数を断定しない。セーブ規模と端末性能で変わる。
  「約 1〜2 分」のような幅で示す。
- **「閉じないでください」を必ず含める。** 今回の事象の直接原因である。
- 色や記号だけに意味を持たせない。文字で伝える。

### 3.3 DoD

- `restore-startup` を選ぶ前に、所要時間と「閉じるな」が**必ず**目に入る。
- `local-only` / `publish` でも、アーカイブ待ちがあることが分かる。
- 既存のボタン配置・既定値・遷移規則（安全方向のみの降格）を変更していない。

## 4. T-F2: 段階進捗の標準エラー出力

### 4.1 機構

`LaunchWorkflow` に進捗シンクを注入する。既存の `state_hook` と同じ形を踏襲する。

```python
ProgressSink = Callable[[str], None]   # 引数は WorkflowState の値のみ

class LaunchWorkflow:
    def __init__(self, ..., progress: ProgressSink | None = None) -> None: ...
```

`_at()` の中で、**監査ログ書き込みが成功したあとに**シンクを呼ぶ。

### 4.2 厳守事項（ここを外すと安全性が壊れる）

- **進捗描画の失敗は握り潰す。** `_at` の監査ログ失敗は現在 `logging_failed` で
  中断する fail-closed 契約だが、**進捗は best-effort である**。
  シンクの例外が mutation 後の処理を中断したり、recovery を隠したりしてはならない。
  `try/except Exception: pass` で包むこと。
- **出力先は標準エラーのみ。** stdout は `_render()` の契約であり、
  `--json` の機械可読出力を汚してはならない。
- **`--json` 指定時は進捗を抑止する。** 自動実行を静かに保つ。新しいフラグは追加しない。
- **出力してよいのは state 名と経過秒数のみ。** パス、root hash、commit OID、
  キャラクター名、remote URL を絶対に含めない。監査ログと同じ許可リスト規律を適用する。
- 状態遷移の順序・タイミングを変更しない。進捗は観測であって制御ではない。

### 4.3 表示内容

- 各状態の開始時に 1 行。
- 長時間になりうる状態（§0.2 で一覧化したもの）には、
  直前の行に所要時間の目安を添える。
- 状態の完了時に経過秒数を出す。利用者が「進んでいる」ことを確認できるようにする。

例（文言は実装時に調整してよい）:

```
[    0.0s] SESSION_START_SNAPSHOT  起動前データを保全しています（約20秒）...
[   17.2s] SESSION_START_SNAPSHOT  完了
```

### 4.4 DoD

- `restore-startup` の 75〜90 秒間、少なくとも 3 回は画面が更新される。
- `--json` の stdout が従来と 1 バイトも変わらない。
- 進捗シンクが例外を投げても、workflow の結果と終了コードが変わらない。
- 監査ログに新しい項目が増えていない。

## 5. T-F3: GUI 進捗表示（要判断。安易に着手しないこと）

**この項目は設計判断を伴う。実装前に §5.2 の結論を出すこと。**

### 5.1 動機

disposition 確認ダイアログを閉じたあと、GUI 起動の利用者の画面には何も残らない。
コンソールは出ている（`shortcut.py:174` により `python.exe` が対象）が、
背面に隠れている可能性がある。

### 5.2 検討すべき選択肢と、それぞれの危険

| 案 | 内容 | 危険 |
|---|---|---|
| A | Tk 進捗ウィンドウを出し、workflow はメインスレッドのまま各段階の合間に `update()` を呼ぶ | 各段階の実行中（17〜21 秒）はイベントループが回らず、Windows がウィンドウを灰色にして「応答なし」と表示する。**ハングに見えるという当初の問題が悪化しうる** |
| B | workflow をワーカースレッドで走らせ、Tk をメインスレッドに置く（`load_catalog_in_worker` と同型） | **ミューテーションがワーカースレッドへ移る。**§2 の非目標に抵触する。lock / state / live 書き換えのスレッド安全性を全面的に再検証する必要があり、費用と危険が大きい |
| C | GUI は出さず、T-F1 の事前告知と T-F2 のコンソール出力のみとする | 追加の危険なし。コンソールが背面にある場合の視認性のみが残課題 |

### 5.3 推奨

**まず C を採用する。** T-F1 + T-F2 で今回の事象は防げる。
A は「応答なし」表示により逆効果になりうるため、実装するなら
段階の合間だけでなく実行中もイベントループを回せる設計（= B）が必要であり、
それは安全境界の再検証を伴う独立した大きな作業である。

C を採ったうえでなお視認性が不足する場合に限り、B を独立チケットとして起こす。
その際は「ミューテーションのスレッド安全性」を最初の検討項目とすること。

### 5.4 DoD（C を採る場合）

- GUI 進捗ウィンドウを追加していないことが、判断理由とともに記録されている。
- コンソールが確実に存在することが実機で確認されている
  （ショートカット起動・PowerShell 起動の両方）。

## 7. 将来の別チケット候補（この計画では実装しない）

### 7.1 コピー回数の削減

`restore-startup` はセーブを 3 回まるごとコピーする。

1. session-start アーカイブ → `staging/<session>-exit-restore`
2. live → `archives/save-before-restore-<session>-exit-restore`
3. `staging/...` → `.save-sync-stage-<session>-exit-restore`

このうち 1 は、アーカイブ自体が既に検証済みの不変ディレクトリであるため、
原理的には省略して 3 で直接アーカイブから stage へコピーできる可能性がある。

**ただし安易に削ってはならない。** 現在の設計は
「復元元は必ずツール所有の staging に一度落とす」ことで、
アーカイブ本体を復元処理中の事故から隔離している。
削減する場合はこの保証を別の手段で維持できることを示す必要がある。

同様に、`stable_manifest` の `retries=3` / `window_seconds=3` は
ゲームの遅延書き込みを吸収するための設定であり、**復元処理中（ゲームは既に終了）**
には過剰な可能性がある。ここも独立に検討する価値がある。

いずれも**性能最適化であり、安全性の緩和と紙一重である。**
別チケットとして、根拠と再検証を伴って扱うこと。

### 7.2 中断からの再開

現在、`restore-startup` が中断すると `recover` は
「ロックをクリーンに破棄」する（live は無変更のまま）。
復元は再実行されない。利用者は次回起動の選択画面で session-start 候補を
手動で選び直す必要がある。

これを「中断した復元を再開する」まで持っていくかは、
fail-closed 契約との兼ね合いがあるため独立した設計判断である。

## 9. テスト

### Unit

- 進捗シンクが `None` のとき、既存の挙動と完全に一致すること。
- 進捗シンクが例外を投げても、workflow の戻り値・終了コード・
  状態遷移・監査ログが変わらないこと。
- 進捗出力にパス・root hash・commit OID・キャラクター名・remote URL が
  含まれないこと（許可リストの検証）。
- `--json` 指定時に stdout が従来と一致し、進捗が抑止されること。

### Integration

- `restore-startup` の一巡で、進捗が 3 回以上出ること。
- 進捗出力の有無で remote head / state / lock / アーカイブが変わらないこと。
- T-F1 の文言が確認ダイアログとラジオの双方に出ていること。

### Regression

- `doctor` / `status` / `recover` / `restore --drill` / `snapshot` / `preserve`。
- bootstrap / enroll / shortcut create-only。
- 3 つの disposition すべての終了後状態（`publish` 経路を含む）。
- 既存の `--json` 出力の全コマンド。

## 10. 維持する安全境界

- 選択・承認前に live、remote main、state、lock を変更しない。
- 三者比較（live / remote / baseline）と fail-closed 判定を維持する。
- ff-only、create-only、archive-before-mutation を維持する。
- opaque `candidate_id` と短命 catalog token を維持し、外部入力から ref を組み立てない。
- 監査ログに追加してよいのは時刻と status のみ。hash、パス、キャラクター名、
  remote URL は追加しない。**進捗出力にも同じ規律を適用する。**
- ゲーム実行中の catalog / restore / promote は従来どおり拒否する。
- **ミューテーションのスレッド配置を変更しない。**

## 11. ワーカーへの指示

- T-F1 を飛ばして T-F2 から始めないこと。最小コストで事象を防げるのは T-F1 である。
- 進捗描画を fail-closed にしないこと。監査ログとは扱いが逆である。
- 既存の未追跡・未コミット変更を削除、reset、checkout しないこと。
- 実セーブと private remote を使う検証は、unit / integration 合格後に、
  明示承認を得てから行うこと。
- 実 remote main を変更する前に、対象 head の managed bookmark を作成して remote 検証すること。
- 性能改善（§7）をこの計画に混ぜないこと。安全性の再検証を伴うため独立して扱う。
- 完了報告には、変更ファイル、テスト結果、実機確認の有無、remote 変更の有無、
  T-F3 の判断結果とその理由、残課題を含めること。

## 12. 完成判定

1. `restore-startup` を選択する前に、所要時間の目安と「閉じるな」の警告が表示される。
2. 長時間処理の最中に、画面が定期的に更新され、進んでいることが分かる。
3. `--json` の stdout が従来と一致している。
4. 進捗機構の failure が、workflow の結果にも recovery にも影響しない。
5. 進捗出力に hash、パス、キャラクター名、remote URL が含まれない。
6. 各 disposition の所要時間の目安が運用ドキュメントに記録されている。
7. 最終状態に lock、recovery phase、Vault 差分が残らない。
